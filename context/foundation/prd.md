## Vision & Problem Statement

People with digestive complaints (stomach pain, heartburn, bloating, bowel issues) cannot reliably connect food to symptoms. Traditional food journals fail because entries are made retrospectively from memory, and wellbeing is tracked rarely and irregularly — leaving no reliable dataset to discuss with a doctor or dietitian. Patterns are invisible; there is nothing concrete to bring to a specialist.

Timing is the innovation. Triggered check-ins at the right moment (1.5–3h post-meal, plus fixed morning and evening check-ins) capture symptoms before they are forgotten. Generic tracking apps do not prompt at the right time; they require the user to remember to log retroactively. MealMirror places the check-in in the user's path at the moment symptoms would still be fresh — making reliable data capture a function of product design, not of the user's memory.

## User & Persona

**Primary persona**: The author — a single named user managing recurring digestive issues. MVP is a personal tool; no account system, no multi-user complexity, no onboarding flow. Product ambition is dozens to ~100 users; architecture must not assume single-user globally, but multi-user features are explicitly deferred to v2.

The persona:
- Has recurring digestive complaints and suspects food triggers
- Wants reliable data to bring to a doctor or dietitian
- Is motivated to track consistently but needs timing prompts and a low-friction interface
- Does not need calorie counts, macros, or food photos — wants minimum viable friction

## Success Criteria

### Primary
Over 2 weeks of continuous use, data completeness ≥ 70%: responses on scheduled/triggered check-ins vs. check-ins generated by the system.

### Secondary
Timeline view allows the user to find how she felt after a specific meal from several days ago in under 1 minute.

### Guardrails
- Every logged meal must have at least one temporally linked check-in within the system's tracking window.
- Adding a new client type (e.g., mobile app) must not require changes to backend domain logic — the API is the single source of truth for all business rules.

## Functional Requirements

### Meal logging
- FR-001: User can log a meal with date, time, and free-text description. Priority: must-have
  > Socrates: Counter-argument accepted: "Free text is too unstructured — patterns may be hard to spot without some categorization." Resolution: kept as free-text for MVP; adding optional tags or a rough category is an open question. See Open Questions.

### Authentication
- FR-002: User can log in via email + password (or magic link). Priority: must-have
  > Socrates: No counter-argument; stands as written. Login is necessary even for a single user to allow access from any device.

### Check-in engine
- FR-003: User can see a list of pending check-ins when they open the app. Priority: must-have
  > Socrates: Counter-argument accepted: "A pending queue only works if the user opens the app — if they forget, the check-in window passes silently, making ≥70% completeness structurally at risk." Resolution: kept; the user will build the daily-open habit. Risk logged in Open Questions.
- FR-004: User can complete a post-meal check-in with a binary tick per symptom (stomach pain, heartburn, bloating, bowel issues, general wellbeing, dryness in mouth). Priority: must-have
  > Socrates: FR revised. Counter-argument accepted: intensity scale adds complexity with marginal value — a symptom is uncomfortable regardless of intensity; binary (present/not) is sufficient for most symptoms. Scale dropped; binary tick replaces it.
- FR-005: User can complete a morning check-in (general wellbeing, skin condition) with binary tick per symptom. Priority: must-have
  > Socrates: Counter-argument accepted: "Skin condition is too subjective without a defined rubric." Resolution: skin condition captured as binary tick for MVP; rubric definition (e.g., clear / mild / severe) deferred to Open Questions.
- FR-006: User can complete an evening check-in (general wellbeing, bowel) with binary tick per symptom. Priority: must-have
  > Socrates: No counter-argument; stands as written. Evening is an end-of-day summary distinct from post-meal reactions.

### Timeline
- FR-007: User can view a timeline of meals and check-ins in chronological order, with visual separation between entry types. Priority: must-have
  > Socrates: Counter-argument accepted: "A flat timeline is hard to read if meals and check-ins scroll together without separation." Resolution: FR updated to require visual differentiation between meals and check-ins. Implementation approach (grouped cards, lanes, color coding) is downstream.
- ~~FR-008: Date range filter on timeline. Priority: nice-to-have~~
  > Socrates: Dropped from MVP scope. Counter-argument accepted: "With only 2 weeks of data, a date filter solves a problem that doesn't exist yet." Deferred to v2.
- FR-008: User can set quiet hours during which post-meal check-ins are not added to the pending queue. Priority: must-have

### Data export
- FR-009: User can export all meals and check-ins as CSV or JSON. Priority: must-have

## Non-Functional Requirements

- Any user-initiated action — meal log submit, check-in submit, timeline load — is acknowledged within 1 second as perceived by the user. The app is used in-the-moment; lag breaks the tracking habit.
- Health data is accessible only via an authenticated session. No health data is shared with third-party services, analytics providers, or external systems. No passive telemetry is collected.
- All stored data (meals and check-ins) is exportable on user request in CSV or JSON format, in a form usable in a spreadsheet or shareable with a doctor or dietitian.
- The product is fully usable in the current major versions of desktop Chrome, Firefox, and Safari. Mobile browser support is deferred to v2.
- The product never surfaces a diagnosis, intolerance verdict, or causal claim. Raw co-occurrence patterns may be presented (e.g., "heartburn appeared on 4 of 5 days following meals containing X"), framed as user-discoverable observations, not system verdicts.

## Business Logic

The app schedules check-ins based on meal timing — 90 minutes after a meal is logged — not based on clock time alone.

After a meal is recorded, a post-meal check-in becomes due 90 minutes later and appears in the user's pending queue on next app open. If a second meal is logged before the first meal's check-in has been answered, the user is asked whether to keep the first check-in at its original time (90 min after meal 1) or defer it (90 min after meal 2). Deferral replaces the pending check-in with a single new check-in due 90 minutes after the second meal.

The user can configure a quiet hours window (e.g., 23:00–07:00). Post-meal check-ins that would fall within the quiet hours window are suppressed — not queued. Morning and evening fixed check-ins are not affected by quiet hours.

## Access Control

Single user (the author). Login is required: email + password or magic link. No registration flow; the account is seeded directly. No role separation — the authenticated user has full access to all data and all actions in the product.

An unauthenticated request to any protected route is rejected and redirected to the login screen.

## Non-Goals

- **No automatic analysis or diagnostic verdicts**: the product shows raw co-occurrence data only. No inference engine, no "you're probably intolerant to X." Diagnostic claims require clinical validation; they are out of scope and potentially harmful without it.
- **No mobile app (iOS/Android native)**: web browser only for MVP. Native mobile is deferred to v2.
- **No multi-user accounts or onboarding flow**: MVP is single-user (the author). Registration, invitations, and shared features are deferred.
- **No food database, calorie counting, macro tracking, or photo logging**: meal entry is free-text description only. Nutritional data is not a concern of this product.
- **No push notifications or background jobs**: the trigger mechanism is pending-queue-on-login only. No email reminders, no service workers.
- **No Apple Watch or other wearable integration**: data entry is manual only for MVP.
- **No HealthKit, sleep, HRV, or activity data integration**: scope is limited to self-reported meals and symptoms.

3. **FR-003 — completeness risk**: the ≥70% data completeness goal depends on the user opening the app within the check-in window. With no reminder mechanism, this is a behavioral commitment, not a system guarantee. Risk acknowledged. Owner: user. Block: no.
4. **FR-005 — skin condition rubric**: skin condition is captured as a binary tick for MVP, but is subjective without a defined rubric. Should "clear / mild / severe" or another scale be adopted? Owner: user. Block: no (binary tick proceeds for MVP).
5. **Pain type priority**: whether decision paralysis ("which food to avoid") is equally central alongside data-trapped and communication-gap pain types — and whether the product surface should reflect that. Owner: user. Block: no (MVP scoped to data capture and timeline; analysis is out of scope).
